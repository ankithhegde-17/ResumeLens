# Email login update: new sender Gmail and complete OTP codes

## What this update fixes

The original app's HTML input and Python validation required exactly six digits. A Supabase project sending eight digits could therefore send a valid code that the app refused to accept. Both layers now accept 6–10 ASCII digits in Supabase mode. The complete string, including leading zeros, is sent to Supabase for verification. Local demo mode still requires its generated six-digit code. Existing CSRF protection, attempt limits and server-side sessions remain in place.

Use the entire newest code. Do not take its first or last six digits. This update does not change the OTP that Supabase generates and does not bypass verification.

## Install the small update ZIP on your existing Windows project

1. Stop Flask with Ctrl+C in its terminal.
2. Back up your project folder using File Explorer.
3. Extract `Multimodal_Resume_Analyzer_Email_Fix.zip` into the existing project folder containing `app.py`, choosing to replace the included files. The ZIP contains no `.env`, databases, tokens, secret keys or virtual environment. Your local configuration and history files are not replaced.
4. Do not extract into `venv312` or create an extra nested project folder. The updated `auth.py` must sit beside your existing `app.py`; `verify.html` belongs in `templates`.
5. No new dependencies or SQL migrations are needed. In VS Code's terminal run:

```powershell
.\venv312\Scripts\python.exe check_setup.py
.\venv312\Scripts\python.exe app.py
```

6. Open http://127.0.0.1:5000/login and press Ctrl+F5 to reload the page. Request a fresh code, wait for the latest email, and enter all digits. Cloud mode shows a 6–10 digit hint; demo mode still shows the terminal-code hint.

## Change the Gmail address used to SEND OTP emails

This changes the application's sender identity. Each student continues signing in with their own email. If you instead sign in as a different student email, that is a different account and will not automatically have the old account's analysis history.

1. Sign into the NEW sender Gmail's Google account.
2. Turn on 2-Step Verification in the Google account's Security settings.
3. Open https://myaccount.google.com/apppasswords while signed into the NEW account. Create an app password named `Resume Analyzer`. Some school/work or Advanced Protection accounts may not offer app passwords; use a supported account or another SMTP provider in that case.
4. Open your Supabase project, then Authentication -> Emails -> SMTP Settings (sometimes labeled Custom SMTP).
5. Keep custom SMTP enabled and save all these settings together:

| Field | Value |
|---|---|
| Sender email address | The new full Gmail address |
| Sender name | Multimodal Resume Analyzer |
| Host | smtp.gmail.com |
| Port | 587 |
| Minimum interval per user | 60 seconds |
| Username | The same new full Gmail address |
| Password | The NEW account's app password, without formatting spaces |

6. Click Save changes. A password generated by the old Google account cannot authenticate the new account.
7. SMTP credentials belong in Supabase. The app uses the same `.env` project URL and publishable key; a sender change does not require replacing these, recreating the database, or editing user records.
8. Request a new OTP from the app and check the message's actual From address. It should show the new sender. Wait at least the configured resend interval before another request.

The project shown earlier in this session uses `https://wxnedyjnnzfshpafjtvx.supabase.co`. Use the URL shown in your own dashboard if working with another project. `APP_MODE` must be `supabase`, and `SUPABASE_PUBLISHABLE_KEY` must be your project's complete publishable key.

## OTP length and template

You can keep eight-digit codes. Supabase supports 6–10 digits; the updated app accepts that range and delegates validity and expiry to Supabase. If you prefer exactly six digits, open Authentication -> Sign In / Providers -> Email, find Email OTP length, set it to 6 if the dashboard offers the setting, and save. Request a NEW code afterwards. Do not change expiry when you mean to change length, and do not truncate an older eight-digit code.

In Authentication -> Email Templates -> Magic Link, use the subject `Your Resume Analyzer sign-in code` and this short body. Use the same numeric-code body for Confirm signup if new-account messages otherwise contain a link.

```html
<h2>Your sign-in code</h2>
<p>Enter this code in Resume Analyzer:</p>
<p><strong>{{ .Token }}</strong></p>
<p>If you did not request this code, ignore this email.</p>
```

Save the template. `{{ .Token }}` must remain exactly as written. Templates display the generated code; editing a heading to say "six digits" does not change its length. Email confirmation should remain enabled.

## Reduce messages going to Spam

An application cannot force delivery to every recipient's Inbox. Gmail's filtering and the sender's reputation also matter; a new Gmail account is not a guarantee of better delivery.

- Use the same actual Gmail address for Sender email and SMTP Username and authenticate using that account's app password.
- Keep the subject and body short and focused on the requested sign-in code. Avoid promotional text, images, attachments and unnecessary links in the authentication email.
- On a recipient's Gmail account, open a genuine requested OTP email in Spam and click Not spam. Add the new sender to contacts if desired.
- For your own demo mailbox, create a filter: Gmail search options -> From = the new sender address -> Create filter -> Never send it to Spam -> Create filter. This affects that recipient mailbox only, not all application users.
- Respect resend limits rather than clicking Send repeatedly. Supabase Auth logs can help distinguish a sending error from a successfully sent email that was filtered.
- For wider use, a transactional SMTP provider with a verified domain and SPF/DKIM/DMARC is a future improvement. You do not need to configure DNS records for a personal `gmail.com` address that you do not own.
